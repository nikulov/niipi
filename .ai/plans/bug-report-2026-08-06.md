## P0 — ломает пользовательский поток

### 41. SMTP отваливается на проверке TLS-сертификата — почта не уходит вообще

**Симптом:**

```
production.ERROR: Connection could not be established with host "ssl://mail.niipigrad.ru:465":
stream_socket_client(): Peer certificate CN=`*.hosting.reg.ru'
did not match expected CN=`mail.niipigrad.ru'
```

**Трасса:** `app/Jobs/SendFormSubmissionEmails.php:61` (`PendingMail->send()`)
→ `symfony/mailer/Transport/Smtp/Stream/SocketStream.php:154`.

**Частота:** все попытки отправки с 06.08 15:06. Успешных нет ни одной.

### Механизм

`MAIL_HOST=mail.niipigrad.ru` резолвится в `31.31.197.112`, PTR —
`server319.hosting.reg.ru` (shared-хостинг reg.ru, Exim 4.99.5). Хост отдаёт
только wildcard хостера, имени домена в сертификате нет:

| | |
| --- | --- |
| Subject | `CN = *.hosting.reg.ru` |
| SAN | `DNS:*.hosting.reg.ru`, `DNS:hosting.reg.ru` |
| Издатель | GlobalSign GCC R6 AlphaSSL CA 2025 |
| Срок | 02.02.2026 → 06.03.2027 |

Сертификат валидный и не просрочен — он просто **не для этого имени**.
PHP проверяет `verify_peer_name`, имя не совпадает, соединение рвётся до
авторизации. На `:587` со STARTTLS отдаётся ровно тот же сертификат —
сменой порта не обходится. По имени `server319.hosting.reg.ru` цепочка
проверяется чисто (`Verify return code: 0 (ok)`).

Конфиг почты (прод `.env`):

```
MAIL_MAILER=smtp
MAIL_HOST=mail.niipigrad.ru
MAIL_SCHEME=smtps      # implicit TLS
MAIL_PORT=465
MAIL_USERNAME=nipi_info@niipigrad.ru
MAIL_FROM_ADDRESS="nipi_info@niipigrad.ru"
```

### Когда сломалось

| Когда | Что |
| --- | --- |
| 05.08 15:07:23 | заявка **1107** (форма 1001) — письмо ушло, `status=sent` |
| 06.08 15:06:33 | заявка **1108** (форма 1006) — первая же отправка падает |

Между этими точками на нашей стороне ничего не деплоилось (релиз от 15.07).
Сертификат подменил хостер.

**Это не рецидив мартовского падения.** В `failed_jobs` есть запись от
03.03 13:00 по тому же хосту и порту (учтена в #40), но там другое
исключение — `Unable to connect to ssl://mail.niipigrad.ru:465
(Connection timed out)`, то есть коннект не устанавливался вовсе.
Расхождение CN — новое.

### Что уже потеряно

Заявка **1108** прошла все 5 попыток (`tries = 5`, `backoff = [60, 300, 900]`)
и в 15:42:41 упала в `failed_jobs` — uuid `e35f7cf8-2681-49ee-97f8-a6ad307e290d`.
Отметки в логе: 15:06:37, 15:07:37, 15:12:38, 15:27:40, 15:42:41.

Затем в 18:59:06 её переотправили из админки (кнопка в
`app/Filament/Resources/FormSubmissions/Schemas/FormSubmissionForm.php:53` —
единственный, кроме `SubmitFormAction.php:86`, диспетчер задачи; планировщика
в проекте нет, `schedule:list` пуст). Второй заход тоже падает: 18:59:06,
19:00:06, 19:05:06, дальше 19:20:06 и 19:35 — после чего заявка снова уйдёт
в `failed_jobs`.

**Сама заявка не потеряна** — `FormSubmission` пишется в БД до отправки писем.
Не ушло только письмо: и админу, и пользователю.

### Как чинить

1. **Быстро, в `.env` прода** — `MAIL_HOST=server319.hosting.reg.ru`.
   Логин/пароль и `MAIL_FROM_ADDRESS` не меняются, SPF/DKIM не задеты.
   Минус: при миграции аккаунта reg.ru на другой сервер номер поменяется
   и почта отвалится снова — с этим же симптомом.
2. **Правильно, у хостера** — заявка в reg.ru на выпуск SSL для
   `mail.niipigrad.ru` (у них есть бесплатный Let's Encrypt на почтовый
   поддомен). После этого вернуть `MAIL_HOST=mail.niipigrad.ru`.
3. **Костыль, не делать** — отключить `verify_peer`/`verify_peer_name` через
   stream options в `config/mail.php`. Работает всегда, но снимает защиту от
   MITM на канале, по которому уходит пароль почтового ящика.

Порядок: сделать (1), чтобы формы заработали сейчас, параллельно запустить
(2) и после ответа хостера откатить `MAIL_HOST` обратно.

Применение (1) на проде:

```bash
# в shared/.env заменить MAIL_HOST
php artisan config:clear && php artisan optimize
# рестарт воркера, иначе он держит старый конфиг
```

Если успеть до очередной попытки по расписанию бэкоффа — заявка 1108
доедет сама, ручной `queue:retry` не нужен. Иначе:

```bash
php artisan queue:retry e35f7cf8-2681-49ee-97f8-a6ad307e290d
```

### Как проверить, что починилось

```bash
echo | openssl s_client -connect <MAIL_HOST>:465 -servername <MAIL_HOST> \
  -verify_return_error 2>&1 | grep -E "subject=|Verify return code"
```

Ожидаемо: `Verify return code: 0 (ok)`. Затем — тестовая отправка формы и
`status=sent` у новой заявки; в `worker.log` строка `DONE`, не `FAIL`.

## Чем закончилось

Проверено 2026-08-10 с прода. `mail.niipigrad.ru:465` теперь отдаёт свой
сертификат:

| | |
| --- | --- |
| Subject | `CN = *.niipigrad.ru` |
| SAN | `DNS:*.niipigrad.ru`, `DNS:niipigrad.ru` |
| Издатель | GlobalSign GCC R6 AlphaSSL CA 2025 |
| Срок | 02.02.2026 → 06.03.2027 |

`MAIL_HOST` в `.env` прода так и остался `mail.niipigrad.ru` — значит
сработал вариант 2 (SSL у хостера), а быстрый обход через
`server319.hosting.reg.ru` не понадобился и накатывать его больше не нужно.
Отправка живая: в `worker.log` `SendFormSubmissionEmails … DONE` 07.08
(4 раза) и 10.08 в 10:32 и 17:43.

**Хвост.** Заявка 1108 так и не доехала: в `failed_jobs` от неё **две**
записи — `e35f7cf8-…` (06.08 15:42, первый заход) и `1491b4c5-…`
(06.08 19:35, переотправка из админки). SMTP уже работает, так что
`queue:retry` их оживил бы — но письмо ушло бы с протухшим текстом, а второй
uuid пришлось бы удалять отдельно, иначе клиент получит дубль. **2026-08-11:
не оживляли, `failed_jobs` вычищен целиком** — см. правку к #40 ниже.

## Правка к #40

Формулировка «восемь потерянных писем, новых падений с 25.05 нет» больше не
верна: в `failed_jobs` **десять** записей, две последние — заявка 1108 от
06.08 по этому багу (основной заход + переотправка из админки). Разбивка:
1 × коннект-таймаут (03.03), 7 × `TimeoutExceededException` (21.05–25.05),
2 × расхождение CN (06.08).

**Итог 2026-08-11: не оживляли ничего.** `queue:retry` отменён — письма
устарели, а по 1108 два джоба дали бы клиенту дубль. На проде выполнен
`php artisan queue:flush`, `queue:failed` пуст. #40 закрыт.
